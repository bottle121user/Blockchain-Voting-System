1. The Election State Machine: Why Closed Elections Cannot Be Reopened

Yes, preventing an election from reopening once closed is an intentional, core security mechanism of the system.

In electronic democratic systems, post-closure immutability is essential. If an administrator possessed the authority to reopen polls after observing preliminary vote distributions, a compromised or corrupt authority could reopen voting, inject phantom ballots for their preferred candidate, and seal it again undetected.

Smart Contract Finite State Machine (VotingSystem.sol):
CREATED → REGISTRATION → OPEN → CLOSED → FINALIZED
  • Strict Forward Progression: The contract enforces the inState modifier on all mutating methods. Once closeElection() executes, the state permanently transitions to CLOSED.
  • Ballot Rejection: The castVoteRelayed() and castVote() functions strictly assert inState(_electionId, ElectionState.OPEN). Any transaction submitted after closure immediately reverts on-chain.
  • Tally Freezing: Candidate tallies are frozen at the exact block timestamp of closure.
  • Proclamation: The election can only transition from CLOSED to FINALIZED, permanently locking results for historical archive.

B. The Encryption Reality: How Voter Privacy Is Protected

A frequent misconception is that public blockchain vote counts should simply be "encrypted with an AES key." On a transparent EVM smart contract, symmetric keys cannot be stored in bytecode or memory without exposing them to all network participants.

Instead of hiding the public counter, ChainVote encrypts/hashes the linkage between voter identity and the ballot through Cryptographic Nullifiers: 

Nullifier = SHA256( VoterIdentifierHash || ElectionId )
  • The voter authenticates with their National ID / credential, receiving a signed token containing their identifier hash.
  • The relayer submits the vote along with the unique 32-byte nullifier commitment to castVoteRelayed().
  • The contract sets hasVotedNullifier[electionId][nullifier] = true and increments the candidate tally.
  • Zero Linkability: Observers on the blockchain inspect only the nullifier and candidate index; they cannot invert the SHA-256 hash to identify the citizen.
  • Localhost Database Encryption: The local SQLite file stores administrative passwords hashed with bcrypt (cost 12). For production local deployments without cloud servers, SQLite can be bound to SQLCipher (AES-256 whole-database encryption).

3. Public Audits & Monitoring Strategy: Dedicated Page Architecture

A. How the Public Audit Engine Functions

ChainVote uses an Event-Driven Asynchronous Indexer (indexer.js):

  1. Whenever a vote is mined, the smart contract emits an EVM event: VoteCast(electionId, candidateId, nullifier, submitter, timestamp).
  2. The background indexer captures the log, verifies block depth, and writes it into the blockchain_events table.
  3. Deduplication is enforced on (tx_hash, log_index), ensuring zero duplication even across server restarts.
  4. The frontend queries pre-indexed SQL tables in sub-3ms, eliminating slow synchronous RPC queries.

B. Architectural Recommendation: Standalone /audit Explorer

To provide optimal user experience for civic observers, the application separates casual result viewers from technical auditors:

  • Civic Results Page (/results): Designed for voters and the public. Features live candidate vote counts, percentage progress bars, voter turnout metrics, and official winner proclamation cards.
  • Public Audit Ledger (/audit): Designed for journalists, independent election observers, and cryptographic auditors. Features a real-time event stream, block height counters, filterable logs by event type, and an interactive "Verify My Ballot" tool where citizens paste their receipt hash or nullifier to prove their vote was permanently mined into a specific block.

5. Penetration Testing & Threat Analysis: Can the System Be Hijacked?

A defensive cybersecurity assessment was conducted across all system tiers:

Threat Vector 1: Relayer Key Compromise & Ballot Stuffing

Severity: HIGH (Architecture Risk)
Finding: In VotingSystem.sol, castVoteRelayed() requires only that the caller has RELAYER_ROLE and that the submitted nullifier has not been previously spent. The contract does not verify an on-chain registration whitelist of nullifiers.
  • Attack Scenario: If an attacker breaches the backend server and steals ADMIN_PRIVATE_KEY from .env, they could bypass the Express API entirely, generate 10,000 random 32-byte nullifiers, and interact with the contract directly to inflate a candidate's vote count.
  • Defensive Mitigation:
    1. On-Chain Merkle Tree Commitment: When registration closes, publish a Merkle root of all authorized voter nullifiers to the contract. In castVoteRelayed(), require a Merkle inclusion proof verifying that the nullifier belongs to the authorized set.
    2. EIP-712 Signed Voter Intents: Require the voter to sign an EIP-712 structured message in their browser: Vote(electionId, candidateId, nullifier). The contract verifies ecrecover(signature) == voterAddress, preventing the relayer from fabricating votes even if compromised.

Threat Vector 2: Replay Attacks & JWT Session Hijacking

Severity: MEDIUM (Transport Risk)
Finding: Tokens stored in browser localStorage are accessible to Cross-Site Scripting (XSS) or network eavesdropping if served over plaintext HTTP.
  • Attack Scenario: An attacker on the same local network intercepts a voter's JWT and casts a ballot before the legitimate citizen.
  • Defensive Mitigation: Migrate from localStorage to HttpOnly, Secure, SameSite=Strict cookies. Bind session tokens to the client's IP and User-Agent fingerprint.

Threat Vector 3: Denial of Service via Relayer Nonce Desynchronization

Severity: MITIGATED BY NONCEMANAGER
Analysis: Flooding the server with concurrent vote submissions would normally cause Ethereum nonce collisions (NONCE_EXPIRED).
  • Defense in Place: ChainVote implements a serialized promise queue (nonceManager.js). Transactions are assigned monotonically increasing nonces in memory. If an RPC error occurs, the manager automatically queries getNonce('pending') to resynchronize before processing subsequent queue items.

Threat Vector 4: Local Database Tampering

Severity: MITIGATED BY ON-CHAIN BACKSTOP
Analysis: An attacker with local OS access directly modifies chainvote.sqlite and sets has_voted = 0 to attempt a second vote.
  • Defense in Place: The attack fails on-chain. When the backend submits the transaction, the smart contract evaluates hasVotedNullifier[electionId][nullifier]. Because the EVM state was permanently marked as spent during the first vote, the transaction reverts with: "VotingSystem: Double voting rejected - nullifier already spent".
